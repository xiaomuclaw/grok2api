# Grok2API 自动 4K 图片放大设计

Status: draft

日期：2026-08-13

## 1. 目标

把图片放大能力内建到 Grok2API 的正常生图链路中。下游只调用一次 Grok2API，并在原有请求中携带模型、提示词、`resolution`、`aspect_ratio` 和 `n`；当 `resolution` 为 `4k` 时，Grok2API 自动请求该上游线路能够提供的最高原生图片，再在交付前将每张图片按原比例放大到长边 4096。

最终结果必须满足：

- Console 和 Web 图片生成共用同一套放大实现。
- URL 和 `b64_json` 返回的是同一份处理后的图片。
- `n` 张结果逐张处理，全部达到目标才返回成功。
- 下游不需要管理员权限，也不需要调用第二个放大接口。
- 1K、2K 和未传 `resolution` 的现有行为保持不变。
- 4K 请求不能用未放大的图片冒充成功。

本功能是 CatmullRom 插值放大，不是 AI 超分，不承诺产生上游原图不存在的新细节。

## 2. 非目标

- 不引入 Real-ESRGAN、GPU 或第三方 AI 超分服务。
- 不恢复上游已经返回 404 或当前账号不支持的模型。
- 不让 Grok 上游直接识别 `4k`；上游只接收它原本支持的分辨率。
- 不实现任意像素尺寸输入，公开接口继续使用 Grok2API 的 `resolution + aspect_ratio`。
- 不改变公开媒体 URL 当前的 capability URL 访问方式。
- 不在第一期把放大并发数、插值算法或 JPEG 质量暴露为面板选项。

## 3. 对外接口

### 3.1 请求格式

沿用现有 OpenAI 兼容图片接口：

```json
{
  "model": "grok-imagine-image-quality",
  "prompt": "一座未来城市",
  "resolution": "4k",
  "aspect_ratio": "16:9",
  "n": 2,
  "response_format": "url"
}
```

`resolution` 接受 `1k`、`2k` 和 `4k`，大小写和首尾空格按现有规则规范化。未传时继续使用当前默认值。

### 3.2 4K 的定义

4K 定义为“成品图片长边为 4096 像素”。短边根据上游实际返回图片的宽高比计算，使用一致的整数取整规则。

示例：

| 上游实际图片 | 4K 成品 |
| --- | --- |
| 2048x2048 | 4096x4096 |
| 2816x1584 | 4096x2304 |
| 1776x2368 | 3072x4096 |
| 784x1168 | 2749x4096（按统一取整规则） |

`aspect_ratio` 仍用于请求上游，但本地放大以实际返回图片为准，不拉伸、不裁剪。这样可以兼容不同模型对比例和尺寸的实际实现差异。

### 3.3 返回格式

- `response_format=url`：保存处理后的成品，返回该成品的公开 URL。
- `response_format=b64_json`：返回同一份处理后字节的 base64。
- 返回结构中已有或能够兼容增加真实 `width`、`height` 的路径应写入处理后的真实尺寸；不能写预期尺寸冒充实测尺寸。

### 3.4 流式请求

`resolution=4k` 与 `stream=true` 不兼容，入口在请求上游前返回明确的 400 错误。原因是当前流式协议会在最终图片处理完成前向下游发送事件，无法保证所有已发送内容都是 4K。

非 4K 流式请求保持现状。

## 4. 请求规划

内部必须分开保存两个概念，不能复用同一个 `Resolution` 字段表达两种含义：

- `RequestedResolution`：下游请求的 `1k`、`2k` 或 `4k`。
- `UpstreamResolution`：实际发送给当前 Provider 的 `1k` 或 `2k`。
- `TargetMaxEdge`：本地成品目标长边；非 4K 为 0，4K 为 4096。

使用明确的 `ImageOutputPlan` 值对象，在选择模型路由后、计费前生成：

```text
ImageOutputPlan
  RequestedResolution = 4k
  UpstreamResolution  = 2k or 1k
  TargetMaxEdge       = 4096
```

规划规则：

| 路线 | 操作 | 4K 请求对应的上游档位 |
| --- | --- | --- |
| Console | 图片生成 | 2K |
| Console | 图片编辑 | 2K |
| Web | 支持 2K 参数的图片生成路径 | 2K，即使上游当前可能静默按 1K 返回 |
| Web Lite | 图片生成 | 1K/当前最高可用档 |
| Web | 当前只接受 1K 的图片编辑路径 | 1K |

Provider 只接收 `UpstreamResolution`，因此不会把 `4k` 传给 Grok。后处理模块只接收 `TargetMaxEdge`，不负责猜测上游档位。

## 5. 统一图片后处理模块

### 5.1 所有权

新增一个统一的生成图片后处理模块，作为以下行为的唯一所有者：

- 解码图片并读取真实方向、宽度、高度和格式。
- 判断是否需要放大。
- 按原比例计算目标宽高。
- 执行 CatmullRom 插值。
- 按格式策略重新编码。
- 校验成品真实尺寸和字节大小。
- 提供处理后的字节、格式、宽高和大小给保存及响应逻辑。

Console 和 Web 不得各自复制尺寸计算、编码或失败回退逻辑。两边只保留很薄的调用代码。

统一后处理返回 `ProcessedImage`，包含：

```text
ProcessedImage
  Bytes
  MIMEType
  Width
  Height
  SourceWidth
  SourceHeight
  Upscaled
```

### 5.2 只放大不缩小

- `TargetMaxEdge=0` 时原样返回。
- 原图长边已经大于或等于目标长边时原样返回，不缩小、不重新编码。
- 原图小于目标时才执行放大。
- 处理后必须重新解码或读取配置，确认真实长边达到 4096。

### 5.3 格式策略

第一版引擎把所有结果强制编码为 PNG，会显著放大 JPEG/WebP 原图的文件体积。新实现采用：

- JPEG 输入：输出 JPEG，质量 95，保留完整色度采样质量。
- PNG 输入：输出 PNG，保留透明通道。
- WebP/GIF 等当前只有解码支持、没有稳定编码器的格式：有透明通道输出 PNG；无透明通道输出 JPEG 95。
- 不为减小体积而丢弃透明背景。
- 输出 MIME、扩展名、数据库记录和响应字段必须一致。

## 6. Console 接入

Console 当前 URL 返回路径会下载上游图片并本地保存；这是 4K 后处理的接入位置。

4K 请求时，无论下游最终需要 URL 还是 `b64_json`，Console 对上游统一请求 URL 结果，然后：

1. 下载原生图片字节。
2. 调用统一后处理模块。
3. 保存处理后的成品。
4. 下游要 URL 时返回成品 URL。
5. 下游要 `b64_json` 时对同一份成品字节编码。

这样避免 Console 的 `b64_json` 旁路绕开放大和本地尺寸校验。

1K/2K 的现有 Console 响应路径保持不变，降低回归和合并风险；只有 4K 使用完整后处理交付路径。

## 7. Web 接入

Web 的图片生成和图片编辑最终都会取得图片字节。取得最终图片字节后、保存或构造 `b64_json` 之前调用统一后处理模块。

必须保证：

- Lite 生图能够使用相同的 4K 后处理。
- WebSocket 图片生成能够使用相同的 4K 后处理。
- 当前可用的 Web 图片编辑路径能够使用相同的 4K 后处理。
- URL 与 base64 都引用处理后字节。
- 4K 的中间 partial image 不输出；流式 4K 已在入口拒绝。

Web 原图可能只有约 1K，放到 4096 的倍数高于 Console。最终像素尺寸满足要求，但画质上限由 Web 原图决定，日志应记录源尺寸和目标尺寸，方便区分上游能力与处理故障。

## 8. 张数、原子性与并发

### 8.1 多张结果

`n` 张图片逐张执行下载、处理和保存。请求只有在全部结果都处理成功后才返回成功。

若第 k 张失败：

- 整次请求返回明确失败。
- 不返回一部分 4K、一部分低分辨率的混合结果。
- 跟踪本次请求已经保存但尚未交付的成品；后续任意一张失败时必须逐一删除。清理失败不改变原请求的失败结果，但必须记录资产 ID 和清理错误供后台处理。
- 不重新请求已经成功生成的上游图片，仅允许对本地保存等明确可重试阶段做有限重试。

### 8.2 放大并发

全进程最多同时执行 2 张 4K 放大。该限制独立于 Web 上游媒体并发和 HTTP 总并发。

- 等待并发槽位时响应请求取消和超时。
- 单个请求的多张图片按顺序处理，避免一次请求独占大量内存。
- 1K/2K 原样交付不占用 4K 放大槽位。
- 并发数第一版固定为 2，不在面板暴露，减少技术配置和升级冲突。

## 9. 文件体积与存储上限

必须区分三个限制：

- Console 原图下载限制：保护从上游读取的 1K/2K 内容，保持现有 32 MiB。
- 外部上传/导入限制：保持现有请求体和 20 MiB 图片导入保护。
- Grok2API 自己产生的 4K 成品限制：允许最高 96 MiB。

不得把所有外部图片入口的全局上限一起提高。媒体服务新增专用的 `SaveGeneratedImage` 入口，让 96 MiB 只适用于已经由统一后处理模块验证过的生成成品；现有 `SaveImage` 和外部导入限制保持不变。

保存前检查：

- 成品字节非空。
- MIME 受支持。
- 真实长边达到目标。
- 成品不超过 96 MiB。
- 媒体总容量仍满足现有容量和清理策略。

超限必须明确失败，不能退回未放大的原图。

## 10. 计费与审计

计费必须使用 `UpstreamResolution`，不能使用下游的 `RequestedResolution=4k`。

例如：

- Console quality 4K：实际向上游请求 2K，按 quality 2K 计费。
- Web 编辑 4K：若实际上游请求 1K，按对应 1K 规则计费。
- 本地插值不额外增加官方上游费用。

预扣、最终审计和失败取消预扣必须使用同一个规划结果。审计日志额外记录以下诊断信息，但不改变现有公开计费字段含义：

- requested resolution
- upstream resolution
- source width/height
- result width/height
- source/result bytes
- upscale duration
- provider
- image count

## 11. 管理面板开关

### 11.1 面板行为

在“运行设置 -> 交付 -> 媒体”区域增加开关：

```text
自动 4K 图片放大
```

说明文案：开启后，Console 和 Web 的 4K 图片请求会在交付前自动放大到长边 4096；1K/2K 不受影响。

### 11.2 配置语义

- 字段：`media.imageUpscaleEnabled`
- 新安装默认值：`true`
- 从旧版本升级且数据库没有该字段：按 `true` 处理。
- 面板保存后通过现有运行设置数据库持久化，并在当前实例及其他实例热更新，无需重启。
- 旧版本管理前端没有发送该字段时，后端保留当前值，不能因 Go `bool` 零值而误关。

关闭后的行为：

- 1K、2K 和未传分辨率的请求保持正常。
- 新的 4K 请求在调用 Grok 上游前明确返回“自动 4K 放大未启用”。
- 已经进入处理阶段的请求使用开始处理时取得的配置快照完成，不在半张图片处理过程中改变策略。

前后端需要同步覆盖：领域设置、运行配置、持久化兼容、HTTP DTO、前端解码器、Zod 表单模型、设置页面、中文和英文文案。

## 12. 失败规则

4K 请求遵循“真的达到 4K，或者明确失败”：

| 阶段 | 行为 |
| --- | --- |
| 功能开关关闭 | 上游调用前返回 400 |
| `stream=true` | 上游调用前返回 400 |
| 上游拒绝或无图片 | 返回现有上游错误 |
| 图片下载失败 | 返回图片下载/后处理错误 |
| 图片无法解码 | 返回图片处理错误 |
| 放大失败 | 返回图片处理错误 |
| 成品长边不是 4096 | 返回尺寸核验错误 |
| 成品超过 96 MiB | 返回成品过大错误 |
| 保存失败 | 返回媒体存储错误 |
| n 张中部分失败 | 整次请求失败 |

不得采用 ChatGPT2API 当前“失败后记录日志并返回原图”的宽松回退。

## 13. 第一版管理端接口

保留现有管理员旧图放大接口，继续用于处理图库中的历史图片，但将其底层实现改为复用新的统一后处理模块。

- 管理端接口不参与下游自动 4K 鉴权链路。
- 不保留两套尺寸计算或编码逻辑。
- 管理端生成的新资产遵守同样的格式和 96 MiB 成品限制。

## 14. 代码组织与上游冲突控制

复杂逻辑放在新增文件，原作者热点文件只保留字段传递和一行调用。按以下职责组织：

1. 图片请求规划：解析 1K/2K/4K，产生 `ImageOutputPlan`。
2. 图片后处理：解码、放大、编码、验证。
3. 可信生成图片保存：保存验证后的成品并返回资产信息。
4. Console 接线。
5. Web 接线。
6. 设置后端和面板开关。

提交历史保持小而完整：

1. `feat(image): add explicit output planning for 4k requests`
2. `feat(media): centralize generated image post-processing`
3. `feat(provider): deliver upscaled images from console and web`
4. `feat(settings): add hot-reloadable 4k upscale toggle`
5. `test(image): cover automatic 4k delivery`

不要把同步原作者代码、4K 功能修改和部署配置揉进同一个提交。

## 15. 验证矩阵

### 15.1 单元测试

- 各种横图、竖图、方图的目标尺寸计算。
- 已达到 4096 时不重新编码。
- JPEG、PNG、透明 PNG、WebP/GIF 回退格式。
- 无效图片、超大图片、取消等待和处理失败。
- 开关旧数据兼容、默认开启、热更新和旧前端字段缺失。
- 4K 规划在 Console/Web 生图和编辑上的上游档位。
- 计费使用上游档位而非 4K。

### 15.2 Provider 合约测试

- Console 4K 对上游发送 2K。
- Console URL 和 base64 都使用处理后字节。
- Web Lite、WebSocket 生图和 Web 编辑都调用统一后处理。
- n 张图片全部被处理。
- 4K stream 在上游调用前被拒绝。
- 关闭开关后没有发生上游调用。

### 15.3 完整回归

- `go test ./...`
- `go vet ./...`
- Swagger 一致性检查。
- 前端 lint 和 build。
- amd64、arm64 镜像构建。

### 15.4 真机验收

至少验证：

- Console 文生图：1K、2K、4K，URL 和 base64。
- Console 图生图：4K。
- Web Lite 生图：1K、4K，URL 和 base64。
- 当前真实可用的其他 Web 图片路径：4K。
- n=1、n=2 和当前允许的最大张数。
- 横图、竖图、方图各一个。
- 开关开、关、重新开启，无需重启。
- 数据库审计费用与实际请求的上游档位一致。
- 下载成品后读取真实像素，不依赖接口文案或日志判断。
- 处理期间观察内存、CPU、耗时和错误日志。

## 16. 发布与回滚

发布版本使用固定标签，例如：

```text
v3.1.2-upscale.2
```

部署步骤：

1. 备份数据库和当前部署配置。
2. 构建并发布固定标签镜像。
3. 服务器只修改 `.env` 中的镜像标签。
4. 拉取并启动新镜像。
5. 完成健康检查和真机 1K/2K/4K 验收。
6. 保留旧镜像标签和备份。

回滚只需把 `.env` 改回上一个固定标签并重新启动；禁止生产环境使用 `main` 或 `latest`。

## 17. 跟随原作者升级

不删除现有 Fork，也不重新 Fork。原作者发布新版时：

1. 保持当前生产标签不动。
2. 拉取 `chenyme/grok2api` 的新标签或 `main`。
3. 从原作者新版本创建 `upgrade/vX.Y.Z` 临时分支。
4. 将本 Fork 的 4K 独立提交重放或合并到临时分支。
5. 重点检查请求规划、Console/Web 结果处理、媒体设置和前端设置页面冲突。
6. 跑完整自动测试和真机验证。
7. 发布 `vX.Y.Z-upscale.1` 镜像。
8. 先部署验证，再把升级结果合入 Fork 的 `main`。

若升级失败，生产仍运行旧固定标签，不受 GitHub 分支同步影响。不要直接在生产前使用 GitHub 网页的 `Sync fork` 覆盖自定义主分支。

## 18. 验收标准

满足以下全部条件才视为实现完成：

- Console 和 Web 的非流式图片路径都复用同一后处理实现。
- 下游使用 API Key 一次请求即可得到 4K 成品。
- 每张 4K 成品真实长边为 4096，比例来自上游实际图片。
- URL 和 base64 内容尺寸一致。
- n 张请求不存在未处理或真假混合结果。
- 1K/2K 现有行为无回归。
- 4K 不被传给 Grok 上游，计费使用实际 1K/2K 档位。
- 面板开关可保存、跨重启保留并热生效。
- 关闭开关和 4K stream 都在上游调用前失败。
- 透明图片不因体积策略丢失透明通道。
- 4K 成品不会被原有 32 MiB 上游下载限制误拦截。
- 完整 CI 和真机验证通过。
- 固定标签镜像可部署，并有已验证的旧版本回滚路径。
