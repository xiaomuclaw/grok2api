# Grok2API 自动 2K/4K 图片交付设计

Status: approved

日期：2026-08-29

## 目标

Grok2API 主要供其他项目通过 OpenAI 兼容接口调用。调用方继续使用现有请求格式：传 `resolution: "2k"` 时获得真实长边 2048 像素的成品，传 `resolution: "4k"` 时获得真实长边 4096 像素的成品。调用方不需要再请求第二个放大接口。

1K 和未传 `resolution` 的行为保持不变。2K、4K 均支持 Console 与 Web 的非流式图片生成和图片编辑路径，并保证 URL 与 `b64_json` 返回同一份处理后的图片。

## 方案选择

考虑过三种方案：

1. 复用 Grok2API 现有统一图片后处理引擎，用一个开关控制 2K/4K。该方案改动集中、调用方式不变，是本次采用的方案。
2. 为 2K 和 4K 分别增加开关。控制更细，但会增加设置、持久化和调用故障判断的复杂度，当前测试服务没有必要。
3. 调用 ChatGPT2API 的放大服务。可以复用另一个部署，但会形成跨服务依赖；任一服务重启或网络异常都会影响图片交付，因此不采用。

## 请求规划

图片请求在选择 Provider 后生成输出计划：

| 调用方请求 | 发给上游 | 本地成品目标 |
| --- | --- | --- |
| 1K 或未指定 | 保持现有值 | 不强制放大 |
| 2K | 上游支持时请求 2K，否则请求 1K | 长边 2048 |
| 4K | 上游支持时请求 2K，否则请求 1K | 长边 4096 |

本地处理以实际下载到的图片尺寸为准，保持宽高比，不裁剪、不拉伸。原图长边已经达到或超过目标时原样保存，不缩小、不重复编码；不足时才使用现有插值引擎放大。

计费和上游审计继续使用实际发给上游的 1K/2K 档位，不能把本地生成的 2K/4K 当成额外的上游费用。

## 设置与兼容性

现有 `media.imageUpscaleEnabled` 字段继续使用，管理面板文案改为“自动 2K/4K 图片放大”。新安装和旧数据库缺少该字段时默认开启。

开关关闭后，1K 请求继续工作；需要本地保障尺寸的 2K/4K 请求在调用上游前明确失败，避免把低分辨率图片冒充成功。开关支持现有的运行时热更新，无需重启。

对外 API 字段和值不变，因此现有调用项目不需要改代码。错误响应沿用当前 OpenAI 兼容结构。

## 处理与失败规则

Console 和 Web 必须继续复用现有统一后处理模块，不能各自实现一套 2K 逻辑。多张图片逐张处理，只有全部达到目标尺寸才返回成功；中途失败时清理本次已保存但尚未交付的图片。

2K/4K 非流式请求遵循“达到请求尺寸，或者明确失败”。流式 2K/4K 继续在上游调用前拒绝，因为当前流式协议无法保证发出的中间结果已经完成尺寸处理。

格式、透明通道、96 MiB 生成成品上限、并发控制和清理策略沿用现有 4K 实现。错误文案中的“4K”统一改为“2K/4K”或“高分辨率图片”，避免调用方误解。

## 测试

必须补充并通过以下验证：

- 输出计划：Console/Web 的 1K、2K、4K 生成与编辑映射正确。
- 2K 请求把不足 2048 的横图、竖图、方图按比例放大到长边 2048。
- 已达到 2048 的图片不重新编码；4K 原有行为不回归。
- URL 与 `b64_json` 都使用处理后的 2K/4K 字节。
- `n > 1` 时每张图片都处理，部分失败不返回真假混合结果。
- 开关关闭时 2K/4K 在上游调用前失败，1K 保持可用。
- 后端 `go test ./...`、`go vet ./...`、二进制构建、前端测试和构建、Docker 镜像构建全部通过。

部署后使用实际 API Key 分别调用 1K、2K、4K，并下载图片读取真实像素尺寸，不能只根据响应文案判断成功。
